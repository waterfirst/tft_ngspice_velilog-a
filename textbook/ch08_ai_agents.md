# 8장. AI 코딩 에이전트와 같이 만들기 — 무엇을 맡기고 무엇을 검증하나

`L3` · 30분 · 코드 없음

---

## 한 문장

Claude Code, Codex 같은 AI 코딩 에이전트는 넷리스트·Verilog-A·피팅 코드를 **빠르게 써주지만 틀린 물리도 자신 있게 써준다.** 그래서 사람이 할 일은 코드를 직접 쓰는 것에서 **"틀리면 반드시 드러나는 검사"를 설계하는 것**으로 옮겨간다.

## 큰 그림

```
 사람: 질문·경계 정하기 ──▶ 에이전트: 코드 작성·실행 ──▶ 자동 검사 ──▶ 사람: 숫자 판정
        (무엇을 채점?)                                   (쌍둥이·정답지·블라인드)      (물리적으로 말이 되나?)
                ▲                                                                        │
                └──────────────────────────── 실패하면 원인 가설과 함께 되돌림 ──────────────┘
```

이 교재 파이프라인에 들어 있는 자동 검사:

| 검사 | 파일 | 잡아내는 것 |
|---|---|---|
| 연기 시험 1 kΩ → 1 mA | `smoke/` | 설치·OSDI 연결 |
| numpy 쌍둥이 ≤ 1e-3 | `check_twin.py` | Verilog-A와 Python 식 불일치 |
| 정답 모델 ≠ 피팅 모델 | `ptft_true.va` vs `ptft_fit.va` | "답 베끼기"로 오차 0이 나오는 착시 |
| 3000 h 블라인드 | `split=blind` | 외삽 과신 |
| 칸별 채점 | `grade.py` | 오차가 어느 칸에서 오는지 |
| 결과 재현 (바이트 비교) | `cmp` | 몰래 바뀐 난수·입력 |

## 비유: 똑똑한 신입 연구원

에이전트는 **밤새 지치지 않는, 문법은 완벽한 신입**이다.

- 시키면 1시간 걸릴 넷리스트를 1분에 써온다.
- 그런데 "PMOS 스캔 신호를 NMOS에 그대로 연결"하거나 "측정 바닥 아래 점을 조용히 지우는" 실수를 **보고서에 안 쓰고** 넘어간다. 결과 그림은 그럴듯하다.
- 좋은 선배는 신입이 쓴 코드를 한 줄씩 읽지 않는다. **"정답이 있는 문제로 먼저 돌려봐"**, **"이 숫자가 왜 이렇게 나왔는지 설명해봐"**라고 시킨다.

## 그래서 뭐 — 이 파이프라인의 함정은 그림만 보면 통과한다

각 장 함정 표와 3장 쌍둥이 검사에서 다룬 문제들을, 결과만 보고 알아챌 수 있는지 기준으로 다시 정리하면:

| 함정 | 틀린 상태에서 결과는 어떻게 보이나 | 잡아내는 검사 |
|---|---|---|
| ngspice `num_threads=8` 기본값 (5장) | 결과는 정상, **느리기만** 하다. "원래 무거운 계산"으로 넘기기 쉽다 | 실행 시간·스레드 수를 숫자로 기록 |
| 측정 바닥 아래 점 삭제 (3장) | 추출은 에러 없이 끝난다. 화소 전류로 채점해야 저계조 +627%가 보인다 | **정답 회로와의 칸별 채점** |
| `limexp` 가짜 포화 (2장) | "TFT 포화 특성"처럼 보이는 곡선 | 선형축 transfer, 오버드라이브 끝까지 스윕 |
| `wrdata -i(V1) -i(V2)` (2장) | 오류 메시지 없음, 숫자도 나온다 | 출력 파일 열 개수 확인 |
| (가상) Verilog-A 수정 후 numpy 식 미수정 (3장) | 추출이 수렴하고 RMS도 작다 | `check_twin.py` |

공통점: **결과만 봐서는 알아채기 어렵다.** 잡는 것은 정답지·쌍둥이·단위·개수 같은 기계적 비교다. 에이전트를 쓰든 안 쓰든 같지만, 에이전트는 코드를 빨리 많이 만들기 때문에 이 검사들이 없으면 틀린 결과도 빨리 많이 쌓인다.

## 에이전트에게 일 시키는 법

**1. 경계부터 준다.**

```
6T1C 화소 시뮬레이션을 ngspice + OpenVAF로 만들어줘.
- 모든 파라미터는 공개 문헌 수준 합성값. 실측·회사 데이터 금지.
- T3, T4는 IGZO NMOS(POL=-1), 나머지 LTPS PMOS.
- 결과는 발광 구간 평균 애노드 전류. 숫자는 결과 파일에서 읽고 손으로 적지 마.
- 끝나면: 사용한 가정 목록, 실패한 시도, 확인 안 한 것을 따로 적어.
```

**2. 검사를 먼저 만들게 한다.** "피팅 코드 짜줘"가 아니라 "피팅 코드가 틀렸을 때 실패하는 검사부터 짜줘".

**3. 숫자로 보고받는다.** "잘 됐다"가 아니라 "블라인드 3000 h 오차 고/중/저 몇 %, 이전 대비 무엇이 바뀌어 몇 %p 달라졌나".

**4. 한 번에 한 가지만 바꾸게 한다.** 3장의 v1→v2는 IGZO 전환과 상한 처리를 동시에 바꿔서 효과 분리가 안 된다. 코드를 빨리 고치는 도구일수록 여러 수정을 한 번에 묶어 보고하기 쉽다.

**5. "왜?"를 두 번 묻는다.** 5장의 "T1만 늙혔는데 −13.7%"에 "보상 회로가 있는데 왜?"라고 물어야 61 mV 보상 부족이 나온다.

## 비유가 깨지는 곳

1. **신입은 배우지만 에이전트는 세션이 끝나면 잊는다.** 함정·결정 사항은 README·SKILL 문서처럼 **파일로 남겨야** 다음 세션이 같은 실수를 안 한다. 이 저장소의 각 장 "실제로 밟은 함정" 표가 그 기록이다.
2. **신입은 모르면 묻지만 에이전트는 모르면 지어낸다.** 존재하지 않는 ngspice 옵션, 틀린 OpenVAF 문법, 없는 논문 수치를 만들어낼 수 있다. 버전을 적고(ngspice 45.2 등) 공식 문서·실행 결과로 확인한다.
3. **"검증했다"는 문장도 검증 대상이다.** 에이전트가 "재현 확인"이라고 쓰면 어떤 명령으로 무엇을 비교했는지 출력까지 보여달라고 한다.

## 데이터 보안

- 실측 CSV, 사내 netlist, PDK, 모델카드를 **외부 AI 서비스에 붙여넣기 전에** 소속 기관·과제 계약의 허용 범위를 확인한다.
- 안전한 기본값: 에이전트에게는 **이 교재 같은 합성 데이터로 파이프라인을 완성**시키고, 실측 데이터 교체는 로컬에서 사람이 한다.
